# 决策单：按 Bot 分配 Skill · 查看已装 Skill · 接入 MCP

> 用途：呈用户一次性拍板。**每项只有 A/B 两选，标 ★ 的是 pm 推荐默认值**；用户不逐条回答时按 ★ 全选推进。
> 关联 PRD：`docs/prd/bot-skills-and-mcp.md`｜日期：2026-10-17｜提出人：用户（房间 `rnd`）

---

## 一句话背景
Skill 安装与 MCP 连接**代码已经有了**，但它们是**全局的**：装了 skill 对所有 bot 生效，MCP 工具一份数组共享给所有 bot。这次要做的是「**按 bot 划范围 + 给 Web 一个能看能改的面板**」。

---

## Q1 交付面：做在哪一层？

- ★ **A. Web UI 为主 + 写进 `my-agent.json`**：在 Bot 设置面板里勾选，配置持久化，重启不丢。CLI 的 `skill add/list/remove` 保留不改。
- B. 只做配置文件（手写 JSON），不做 UI。
- **选 B 的后果**：用户要手改 JSON 才能用，且「查看已装 skill」仍然只能在终端看表格。

---

## Q2 「给 bot 装 skill」的含义？

- ★ **A. 全局装一次 + 每个 bot 勾选白名单**：磁盘上只有一份，bot 只是「能不能看见/加载」。
- B. 每个 bot 独立一份副本（各自目录）。
- **选 B 的后果**：磁盘与升级分裂（同名包 N 份，升级要装 N 次），且与现有 npm 单根安装方式冲突。**pm 不建议**。

---

## Q3 MCP 的作用域？

- ★ **A. server 在全局配置里定义一次 + 每个 bot 勾选启用哪些**：同一 server 多 bot 复用，进程只连一次。
- B. 每个 bot 各自配置自己的 MCP server（名字/命令各写一遍）。
- **选 B 的后果**：同一 server 会被重复起进程，配置面翻倍。**pm 不建议**。

---

## Q4 MCP 传输方式本期做到哪？

- ★ **A. 仅 stdio**（现有实现，够用；不新增依赖）。
- B. 本期同时支持 HTTP / SSE（远程 MCP）。
- **选 B 的后果**：多一层网络鉴权与超时/重连设计，工期显著拉长。**建议二期**。

---

## Q5 老 bot 没配过 skill 时的默认行为？

- ★ **A. 缺省 = 可用全部已装 skill**（= 今天的行为，零破坏）；**用户一旦在面板里保存勾选，就变成严格白名单**（哪怕全不勾 = 一个都不可用）。
- B. 缺省 = 一个都不可用，必须显式勾选。
- **选 B 的后果**：现有 bot 升级后会突然失去所有 skill，属于破坏性变更。

---

## Q6 claude / opencode / pi 这类 CLI backend 的 bot 怎么办？

- ★ **A. 只对 native backend 生效**；UI 对这些 bot 显示「由该 CLI 自行管理」，不写配置、不假装能控。
- B. 也尝试注入（改它们的配置/环境变量）。
- **选 B 的后果**：每个 CLI 行为不同（工具栈自管），要逐个适配且容易误导用户。**建议不碰**。

---

## 拍板后不需要再决策的两条硬约束（pm 已定，仅告知）

1. **作用域必须两处同时收**：① 该 bot 的系统提示不列出未指派 skill；② `load_skill` 对该 bot 拒绝越界名字。只做①等于没做（bot 仍能猜名字加载）。
2. **安全底线**：MCP 的 `env` 密钥**不回传浏览器**（只显示键名 / 已设置）；「安装 skill」「改 MCP 配置」属执行外部命令的写操作，**仅本机访问（loopback）可改**，远程绑定返回 403 + 可读原因。
