## 0. 结论速览（TL;DR）

- **Grok 的 "bot" 有三层含义**：① xAI 官方在聊天产品里跑的**多智能体（multi-agent）协作者**；② 在 X / Telegram 等平台上以账号形式存在的 **@grok 机器人**；③ 开发者用 **xAI API** 自建的第三方 bot。
- **bot 之间的交互**主要有三种模式：**并行协作（Grok 4 Heavy）**、**工具/子 agent 编排（Agent Tools）**、**API 编排的 bot-to-bot 环路**。
- **页面与用户的交互**核心是一条：**「输入 → 模式路由 → 流式渲染 → 可交互产物（引用/代码/Canvas/图片）」** 的闭环，模式选择器（Fast / Think / DeepSearch 等）是最关键的交互分叉点 ⚠️。

## 1. Grok bot 的产品形态盘点

| 形态 | 载体 | 是否"多 bot" | 备注 |
|---|---|---|---|
| Grok 助手 | grok.com 网页 / iOS / Android App | 单助手，内部可多 agent | 消费级主入口 ⚠️ |

| xAI API | `api.x.ai`（OpenAI 兼容） | 由开发者决定 | 自建 bot / Agent / 编排 |

## 2. 重点一：Grok **bot 之间的交互**

### 2.1 Grok 4 Heavy：并行多智能体协作（最核心）
- 思路：对同一个问题**并行拉起多个 Grok agent**，各自独立推理，再由某一层做**汇总/交叉验证/择优**。
- 交互特征（抽象模型）：
  - **同一任务广播**给 N 个 agent；
  - agent 之间**不直接对话**，而是通过**共享任务上下文 + 结果回流**间接交互；
  - 上层进行**仲裁（ensemble / judge）**，产出最终答案。
- 工程含义：这是一个 **"star/仲裁拓扑"** 而非"自由对话拓扑"。对页面而言，用户体验到的是**更长的等待 + 更稳的答案**，因此 UI 上需要"多路进行中"的可视化（进度、分片结果）。
- ⚠️ 具体 agent 数量、是否互相可见、是否投票，需以 xAI 官方说明为准。

### 2.2 Agent Tools / 服务端工具编排
- xAI 提供**服务端工具**（如 Web Search、X Search、代码执行等）⚠️，模型在一个回合内**自主决定调用哪些工具**。
- 这里的 "bot 交互" 表现为：主 agent ⇄ 工具/子服务，**由主 agent 单方发起**，工具返回结构化结果后回到主对话。
- 关键点：工具调用是**可观察事件**（streaming 里会插入 tool-call 帧），直接决定前端要不要画"工具卡片"。

### 2.3 用 xAI API 自建 bot-to-bot
- API 为 OpenAI 兼容 ⚠️ → 很容易搭两个角色（如 A=规划、B=执行）**互相传消息**：
  - A 产出 → append 到 B 的 messages → B 产出 → 回填 A → 循环（带**最大轮数/终止条件**防死循环）。
- 风险与工程约束：
  - **无限对话/费用失控**：必须设定轮数上限、token 预算、超时；
  - **上下文膨胀**：需要摘要/裁剪策略；
  - **环路死锁**：两个 bot 互等 → 需要"发言权"仲裁或明确 stop 条件。

### 2.4 X 平台上的 bot 生态
- `@grok` 可被**用户在帖子里 @提及**触发，并在**被回复帖子的上下文**里作答。
- 由此产生 bot-to-bot 变体：其他自动化账号 @grok、或 Grok 回复中再被第三方 bot 接手。
- 与页面交互强相关：X 内的 Grok 是**"嵌在信息流里的对话框"**，而不是独立聊天页。

### 2.5 Telegram / Discord 等 IM bot
- 典型 IM bot 交互原语：**私聊、群内 @提及、slash 命令、inline 回复、按钮回调**。
- bot-to-bot 在 IM 里较少见（平台通常限制 bot 之间的可见性/刷屏）⚠️，更多是"人→bot"。

### 2.6 交互模式归纳

| 模式 | 发起方 | 拓扑 | 典型产品 |
|---|---|---|---|
| 并行协作+仲裁 | 系统 | star / ensemble | Grok 4 Heavy |
| 工具调用 | 主 agent | 主从 | Agent Tools |
| bot-to-bot 环路 | 开发者编排 | 环/P2P | 自建（API） |
| 账号级回复 | 用户/其他账号 | 树（回复链） | X `@grok` |
| IM 命令/回复 | 用户 | 星形 | Telegram bot |

## 3. 重点二：**页面与用户的交互逻辑**

### 3.1 整体布局（抽象）
```
┌───────────────┬──────────────────────────────────────┐
│ 侧栏 Sidebar  │  对话区（消息流，纵向）              │
│ - 新建会话    │   - 用户消息                          │
│ - 历史/搜索   │   - 助手流式回复                      │
│ - 模式/设置   │     · 思考过程折叠                    │
│               │     · 引用/来源                       │
│               │     · 代码块 / Canvas / 图片          │
│               ├──────────────────────────────────────┤
│               │  输入区 Composer                     │
│               │  [模式选择][附件][语音][发送]         │
└───────────────┴──────────────────────────────────────┘
```
⚠️ 元素名称/位置以实际 UI 为准。

### 3.2 输入区（Composer）交互
- **多模态输入**：文本、图片/文件上传（触发视觉/文档理解）、语音 ⚠️。
- **模式选择**：Fast / Think / DeepSearch / Auto 等（见 3.3）。
- **快捷动作**：改写下提示（"Improve prompt"）、新建会话、清空上下文 ⚠️。
- **发送后**：输入框清空、消息入场、按钮进入"停止生成（Stop）"状态 → 支持**中断**。

### 3.3 模式选择 = 最主要的交互分叉点
- 用户选不同模式 → 后端走**不同的推理/检索管线** → 前端呈现**不同的等待形态**：
  - `Think`：显示**可折叠的推理过程**；
  - `DeepSearch`：显示**检索步骤 + 来源引用**；
  - `Auto`：由系统自动路由（用户无感，但延迟不可预测）。
- 设计要点：**让"模式"对用户是可理解的**，否则"为什么这次这么慢"会成为主要困惑点。

### 3.4 输出渲染与交互
- **流式（streaming）**：逐 token 渲染，配合"停止"按钮与自动滚动（用户上滑时应**暂停自动滚动**）。
- **可交互产物**：
  - 代码块：复制 / 运行 ⚠️；
  - 引用来源：可点击跳转；
  - Canvas/Studio：右侧分栏编辑、可迭代修改 ⚠️；
  - 图片（Grok Imagine）：生成、下载、变体 ⚠️。
- **消息级操作**：复制、重新生成（Regenerate）、继续（Continue）、点赞/踩、分享 ⚠️。

### 3.5 记忆与个性化
- Grok 具备**跨会话记忆 / 个性化**能力，且通常可在设置中开关 ⚠️。
- 交互含义：页面需要暴露**"它记得什么"的可查看/可清除入口**，否则用户无法建立信任（这一点本仓库的 BotMemoryPanel 也是同类思路）。

### 3.6 X 内的嵌入交互
- 与独立页面不同，X 里的 Grok 是**信息流内联**体验：在帖子上下文中唤起、就地作答、可切换为完整会话。

### 3.7 交互状态机（时序抽象）
```
Idle ──(输入/发送)──▶ Submitting ──▶ Streaming(思考/工具/正文) ──▶ Done
                                         │
                                         └──(Stop)──▶ Stopped ⇢ (可 Regenerate)
Streaming 期间可插入：ToolCall 帧、Citation 帧、Reasoning 帧、Image 帧
Error ──▶ 重试入口
```

## 4. 可借鉴的设计结论

1. **"多 agent 并行"必须配 UI 可视化**：否则只是"更慢的等待"。要给用户看见"在跑几路 / 到了哪一步"。
2. **模式选择器是交互核心**：它同时决定延迟、成本、可见内容（思考/来源）。需要清晰的**预期管理**。
3. **流式 + 可中断 + 消息级重试** 是现代 AI 页面的下限体验，缺一不可。
4. **工具调用要作为一等公民渲染**（卡片/时间线），因为它是"bot 之间交互"在 UI 上的唯一可见证据。
5. **记忆需要可见可控**，否则信任成本很高。
6. **bot-to-bot 编排要防死循环/防费用失控**（轮数上限、预算、超时、摘要裁剪）。
